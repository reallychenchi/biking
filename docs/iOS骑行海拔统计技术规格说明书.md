# iOS 骑行海拔统计技术规格说明书

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v1.0 |
| 编写日期 | 2026-07-27 |
| 文档状态 | 已审核，实现基线 |
| 适用范围 | iPhone，iOS 18.0 及以上，本地 SwiftData 骑行记录 |
| 需求目标 | 在骑行详情展示累积上升、累积下降和海拔范围 |

## 2. 审核结论

当前方案方向正确，但“平滑后直接累加相邻点正负高度差”仍会把残留的小幅往返波动重复计入；“相邻点小于固定阈值不计”又会漏掉每次只上升少量、但总高度持续增加的缓坡。因此首版不能只采用其中一个简单规则。

本规格采用以下组合方案：

1. 使用 Core Location 提供的海拔和垂直精度，不接入网络地形服务，不根据经纬度推造海拔。
2. 垂直精度过滤后，以三点中值滤波去除孤立尖峰。
3. 使用 `3 m` 趋势确认阈值和上升/下降状态机累计高度变化。
4. 阈值只用于确认趋势，不从已经确认的真实高度变化中扣除 `3 m`。
5. 不跨轨迹分段或超过连续性时限的定位缺口计算高度差。
6. 保存原始有效定位点的海拔信息，同时在骑行记录上保存完成时的统计结果。

该方案能够避免相邻点阈值导致的缓坡漏算，也能避免平地残余抖动被反复累计。它不承诺达到测绘级精度；参数仍必须通过模拟器确定性测试和真机骑行样本验证。

## 3. 当前代码与数据能力

当前 `CLLocation` 在 `RawLocationSample.init(location:)` 中只转换经纬度、时间、水平精度和速度，`TrackPoint`、`TrackPointEntity`、`RideRecord` 与 `RideEntity` 均没有海拔字段。因此：

- 当前已有轨迹是二维轨迹，不能从现存数据可靠还原设备当时测得的海拔。
- 历史记录不调用外部地形服务补算，也不显示伪造的 `0 m`。
- 功能上线前产生的记录在详情中显示海拔统计不可用。
- 功能上线后，只有具备足够有效海拔样本的骑行才展示对应统计值。

## 4. 范围与非目标

### 4.1 本期范围

- 采集并持久化 Core Location 海拔和垂直精度。
- 计算并持久化累积上升、累积下降、最低海拔和最高海拔。
- 在已完成骑行的“详情”页展示三个海拔统计项。
- 覆盖算法、模型映射、持久化和格式化的单元测试。
- 保持现有轨迹、距离、速度、计时和保存重试行为不变。

### 4.2 本期不包含

- 不使用 MapKit 地图视觉地形反推轨迹海拔。
- 不调用数字高程模型、第三方海拔 API 或自建服务补算海拔。
- 不接入 `CMAltimeter`，不融合气压计相对高度。
- 不为旧记录回填海拔统计。
- 不增加实时海拔、实时爬升或海拔曲线页面。
- 不修改距离、速度和运动时间的现有计算口径。

## 5. 名词与产品口径

| 名词 | 定义 |
| --- | --- |
| 原始海拔 | `CLLocation.altitude` 提供的米制高度值 |
| 垂直精度 | `CLLocation.verticalAccuracy`，单位为米；负值代表无有效海拔精度 |
| 有效海拔样本 | 海拔和垂直精度均为有限数值，且垂直精度位于 `0...20 m` |
| 平滑海拔 | 对同一连续海拔段执行三点中值滤波后的海拔 |
| 有效趋势 | 从候选低点上升至少 `3 m`，或从候选高点下降至少 `3 m` |
| 累积上升 | 所有已确认上升趋势的完整高度增量之和，结果为非负数 |
| 累积下降 | 所有已确认下降趋势的完整高度减量绝对值之和，结果为非负数 |
| 海拔范围 | 所有平滑有效海拔中的最低值到最高值；不对不同分段之间做差值累计 |

“平地”在本规格中的计算定义是：尚未形成绝对幅度至少 `3 m` 的上升或下降趋势。它不是根据地图坡度、道路类型或瞬时速度判断。

## 6. 参数配置

参数必须集中定义在 Domain 层的命名配置中，不得散落在控制器、仓储或 View：

| 参数 | 首版值 | 作用 |
| --- | ---: | --- |
| `maximumVerticalAccuracyMeters` | `20 m` | 排除垂直精度过差的样本 |
| `minimumElevationTrendMeters` | `3 m` | 确认上升、下降及趋势反转 |
| `maximumElevationContinuityGapSeconds` | `30 s` | 超过该时间不跨缺口计算高度差 |
| 中值滤波窗口 | `3` 个有效样本 | 去除孤立的单点尖峰 |

`30 s` 必须与现有轨迹分段时间口径共用同一语义来源，不能复制出两个可能漂移的硬编码值。上述首版参数是实现基线；修改参数必须同时更新规格、命名常量和针对性测试。

## 7. 数据采集与有效性

### 7.1 原始样本

`RawLocationSample` 增加：

- `altitudeMeters: Double?`
- `verticalAccuracyMeters: Double?`

从 `CLLocation` 转换时保留有限数值；非有限值转换为 `nil`，不得写入 SwiftData。负数海拔是合法值，例如低于海平面的区域，不得因为小于零而拒绝。

### 7.2 轨迹点

`TrackPoint` 与 `TrackPointEntity` 增加同名可选字段。字段保持可选有两个原因：

1. 兼容功能上线前已经保存、没有海拔字段的记录。
2. 水平定位有效并不代表垂直定位有效；垂直数据不可用时，轨迹、距离和速度仍应正常记录。

水平轨迹点仍由 `LocationSampleValidator` 按现有规则接受或拒绝。海拔无效不得导致整个水平轨迹点被拒绝，也不得中断距离和速度计算。

### 7.3 海拔参与计算的条件

轨迹点只有同时满足以下条件才进入海拔平滑和统计：

- `altitudeMeters` 存在且为有限数值；
- `verticalAccuracyMeters` 存在且为有限数值；
- `verticalAccuracyMeters >= 0`；
- `verticalAccuracyMeters <= 20`。

不符合条件的点保留其可持久化原始字段，但不参与海拔统计。不能以 `0 m` 代替无效海拔。

## 8. 连续海拔段

先按轨迹点 `sequence` 升序处理。出现以下任一条件时结束当前连续海拔段：

- `segmentIndex` 变化；
- 当前有效海拔样本与前一个有效海拔样本的时间间隔大于 `30 s`。

结束一段时，应完成该段的滤波尾点和已经确认的未结趋势，再开始新段。新段的首个海拔不得与上一段末尾做差。

无效海拔样本本身不立即切段；如果后续有效海拔仍处于同一 `segmentIndex` 且距离上个有效海拔不超过 `30 s`，两者仍属于同一连续海拔段。

## 9. 三点中值平滑

对每个连续海拔段独立执行窗口为 `3` 的中值滤波：

```text
首点：保留原始有效海拔
中间点：median(前一点, 当前点, 后一点)
末点：保留原始有效海拔
```

长度为 `1` 或 `2` 的段保留原值。任何窗口都不得跨连续海拔段。

示例：

```text
原始：100, 130, 100
平滑：100, 100, 100
```

中值滤波用于消除孤立尖峰，不会像移动平均或指数移动平均那样持续削弱单调缓坡。首末点缺少双侧样本，首版保留原值；端点异常属于已知限制，依靠垂直精度过滤和真机验证控制，不增加未经验证的端点补造规则。

## 10. 趋势确认与累计

### 10.1 为什么不直接比较相邻点

如果相邻点每次只上升 `1 m`，简单的“差值小于 `3 m` 不计”会把从 `100 m` 连续上升到 `110 m` 的缓坡计算为 `0 m`。因此阈值必须作用于候选低点/高点形成的完整趋势，而不是作用于单个相邻差值。

### 10.2 状态

每个连续海拔段维护以下状态：

- `undetermined`：尚未形成达到阈值的趋势，同时维护候选最低点和候选最高点；
- `rising(anchorLow, highest)`：已确认上升，维护本轮起始低点和后续最高点；
- `falling(anchorHigh, lowest)`：已确认下降，维护本轮起始高点和后续最低点。

每个新段从 `undetermined` 开始。

### 10.3 状态转换

阈值记为 `T = 3 m`：

```text
undetermined:
  更新候选最低点和候选最高点
  当前高度 - 候选最低点 >= T -> 进入 rising
  候选最高点 - 当前高度 >= T -> 进入 falling

rising:
  持续更新 highest
  highest - 当前高度 >= T ->
    累积上升 += highest - anchorLow
    从 highest 开始进入 falling

falling:
  持续更新 lowest
  当前高度 - lowest >= T ->
    累积下降 += anchorHigh - lowest
    从 lowest 开始进入 rising
```

连续海拔段结束或骑行结束时：

- `rising` 将 `highest - anchorLow` 计入累积上升；
- `falling` 将 `anchorHigh - lowest` 计入累积下降；
- `undetermined` 不累计，因为整段变化没有达到 `3 m`；
- 已经在趋势反转时提交的值不得重复累计。

阈值用于判断趋势是否可信。一旦趋势达到阈值，累计的是完整变化量。例如从 `100 m` 上升至 `104 m`，累积上升是 `4 m`，不是扣除阈值后的 `1 m`。

### 10.4 海拔范围

最低和最高海拔直接取所有连续段中平滑有效海拔的全局最小值和最大值：

```text
minimumAltitudeMeters = min(全部平滑有效海拔)
maximumAltitudeMeters = max(全部平滑有效海拔)
```

允许跨分段比较全局最低和最高值，但绝不把两个分段端点之间的差值计入累积上升或下降。

### 10.5 可用性

- 至少有一个平滑有效海拔时，最低和最高海拔可用。
- 至少有一个连续海拔段包含两个可比较样本时，累积上升和累积下降可用；没有达到趋势阈值时二者均为 `0 m`。
- 只有一个有效海拔时，海拔范围可以显示为相同的最低/最高值，但累积上升和累积下降显示不可用。
- 没有有效海拔时，四个底层统计值均不可用。

这一区分避免把“没有可计算数据”错误展示为“确定爬升了 `0 m`”。

## 11. 领域模型与职责

新增 `Domain/ElevationAccumulator.swift`，集中拥有：

- `ElevationCalculationConfiguration`；
- 有效海拔判断；
- 连续段识别；
- 三点中值平滑；
- 趋势状态机；
- `ElevationMetrics` 输出。

`ElevationMetrics` 建议结构：

```swift
struct ElevationMetrics: Hashable, Sendable {
    let cumulativeAscentMeters: Double?
    let cumulativeDescentMeters: Double?
    let minimumAltitudeMeters: Double?
    let maximumAltitudeMeters: Double?
}
```

`nil` 代表不可用，`0` 代表有足够数据且没有确认的上升或下降。

`RideSessionController.ActiveRide` 持有 `ElevationAccumulator`，每当 `LocationSampleValidator` 接受轨迹点后，将该点交给累加器。View、仓储和 SwiftData Entity 不实现或复制算法。

累加器必须支持：

- 获取不破坏状态的 checkpoint 快照；
- 在结束骑行时生成最终快照；
- 最终化操作幂等，保存失败后的重试必须复用同一个 `RideCompletionSnapshot`，不能重复累计末段。

## 12. 持久化规格

### 12.1 轨迹点字段

`TrackPointEntity` 增加：

- `altitudeMeters: Double?`
- `verticalAccuracyMeters: Double?`

### 12.2 骑行聚合字段

`RideEntity`、`RideProgress` 和 `RideRecord` 增加：

- `cumulativeAscentMeters: Double?`
- `cumulativeDescentMeters: Double?`
- `minimumAltitudeMeters: Double?`
- `maximumAltitudeMeters: Double?`

checkpoint 更新当前统计快照；完成保存以 `RideCompletionSnapshot` 的最终统计覆盖 checkpoint 值，并与剩余轨迹点和完成状态在同一个仓储保存操作中提交。

最终详情以 `RideEntity` 保存的聚合字段为展示来源，不在 View 中遍历轨迹点临时重算。轨迹点海拔作为原始证据保留，方便测试、排查和未来明确授权后的重新计算；本期不实现自动重算或算法版本迁移。

### 12.3 旧数据兼容

新增字段全部为可选值，不给旧记录填充 `0`。实现后必须验证 SwiftData 对现有本地 Store 的轻量迁移：

1. 使用功能上线前的构建创建至少一条骑行记录；
2. 覆盖安装新构建并启动；
3. 确认旧记录、轨迹、距离、时间和速度仍可读取；
4. 确认旧记录海拔项显示 `—`；
5. 确认新记录能够正常保存并在重启后读取海拔统计。

如果现有 Store 无法自动迁移，必须停止实现并设计显式 `VersionedSchema`/`SchemaMigrationPlan`；不得静默删除数据库或清空用户骑行记录。

## 13. 详情页展示

在 `RideDetailInfoView` 的“总距离”之后增加：

| 字段 | 格式 | 不可用 |
| --- | --- | --- |
| 累积上升 | 四舍五入到整数，`123 m` | `—` |
| 累积下降 | 四舍五入到整数，`98 m` | `—` |
| 海拔范围 | 最低到最高，`35–162 m` | `—` |

规则：

- 海拔底层统一使用米，不保存格式化字符串。
- 负海拔必须正确展示，例如 `−12–85 m`。
- 最低值在前、最高值在后。
- 只有范围可用时允许单独显示范围；累积值按各自可用性展示。
- 三行继续使用现有详情行布局和 `monospacedDigit()`，并保持 VoiceOver 合并后的中文含义完整。

## 14. 错误、警告和日志

- 单个垂直精度无效属于定位质量问题，不得让整次骑行失败，也不得逐点输出大量重复日志。
- 骑行完成时如果没有任何有效海拔，记录一条 location warning，详情显示不可用。
- 如果计算结果出现非有限值、负累积值、最低值大于最高值等内部不变量错误：Debug 构建触发断言；Release 构建记录 error，不得静默交换、取绝对值或伪造 `0`。
- SwiftData 保存或迁移失败沿用现有持久化错误处理与显式重试/启动失败路径，不新增静默兜底。
- 骑行和包含海拔统计的完成记录成功保存后，沿用现有 info 级别成功日志；日志不得输出完整轨迹或逐点精确位置。

## 15. 测试规格

### 15.1 领域算法单元测试

至少覆盖：

1. 单调缓坡：`100, 101, 102, 103, 104`，最终累积上升为 `4 m`，证明不按相邻 `1 m` 差值漏算。
2. 单调下降：镜像数据得到对应累积下降。
3. 平地小幅抖动：全部变化未形成 `3 m` 趋势，升降均为 `0 m`。
4. 孤立尖峰：`100, 130, 100` 经中值滤波后不产生虚假升降或范围尖峰。
5. 真实峰顶平台：持续上升、至少两个峰顶样本、再持续下降，分别得到完整上升和下降。
6. 恰好达到 `3 m`：必须确认趋势并累计完整 `3 m`。
7. 未达到 `3 m`：不累计。
8. 趋势反转：一次上升只能提交一次，下降同理。
9. 结束时仍在爬升或下降：最终化时提交已确认的末段，不能漏算。
10. 最终化及保存重试：重复获取最终快照不重复累计。
11. 轨迹分段：不计算前段末点到后段首点的高度差，但两段内部各自累计。
12. 时间缺口超过 `30 s`：行为与分段一致。
13. 无效垂直精度、负垂直精度、非有限值：不参与统计，且不影响水平轨迹。
14. 负海拔：可参与最低、最高和升降计算。
15. 一个有效点、两个有效点、没有有效点的可用性语义。
16. 海拔范围使用平滑值，最低和最高顺序正确。

浮点断言使用明确容差，不能依赖格式化字符串掩盖误差。

### 15.2 模型与仓储测试

- `CLLocation -> RawLocationSample -> TrackPoint -> TrackPointEntity -> TrackPoint` 的海拔与垂直精度映射完整。
- checkpoint 和完成保存正确写入四个统计字段。
- `completedRides()` 映射结果与保存值一致。
- 旧记录可选字段为 `nil` 时读取成功，不转换为 `0`。
- 保存失败重试不会重复轨迹点，也不会重复增加升降值。

### 15.3 格式化和界面测试

- 正数、负数、零值和不可用值格式正确。
- 海拔范围最低值在前、最高值在后。
- 详情页出现“累积上升”“累积下降”“海拔范围”，旧记录显示 `—`。
- 不改变详情页“轨迹”Tab、历史列表排序或轨迹地图。

### 15.4 真机验证

真机验证是发布前必需项，至少采集并保存：

- 一段相对平坦路线；
- 一段已知持续爬坡路线；
- 一段包含上坡和下坡的往返路线；
- 一次后台或锁屏骑行；
- 一次定位质量较差的场景。

验证原始海拔、垂直精度、平滑结果和最终统计，不以地图的三维视觉效果作为正确性证据。首版参数如需调整，必须基于这些样本修改配置和测试预期。

## 17. 实现顺序与验收门槛

1. 增加领域数据字段和纯 Domain 海拔累加器。
2. 先完成并运行算法单元测试。
3. 接入定位样本与 `RideSessionController`，确认不影响现有距离、速度和计时。
4. 增加 SwiftData 可选字段和仓储映射，验证旧 Store 迁移。
5. 增加格式化与详情展示。
6. 更新产品需求和架构文档，使产品口径、代码和规格一致。
7. 运行 `bikeTests`、App build、静态分析和 `git diff --check`。
8. 单独报告 UI 测试、模拟器、真机、实时 GPS、后台/锁屏验证是否实际执行。

实现验收必须同时满足：

- 三个指标符合本规格算法和不可用语义；
- 旧记录不伪造海拔值且其他数据不丢失；
- 新记录重启 App 后统计仍存在；
- 保存失败重试不重复累计；
- 现有距离、速度、时间、轨迹和历史详情行为无回归；
- 没有把海拔计算散落到 View 或持久化层；
- 所有实际运行的检查及未执行的真机验证均如实报告。

## 18. 已知限制

- Core Location 海拔精度通常低于平面坐标精度，本功能是消费级骑行统计，不是测绘结果。
- 三点中值滤波可以消除孤立尖峰，但连续多个错误样本仍可能影响结果。
- 首末点缺少双侧样本，无法使用完整三点窗口。
- 固定 `20 m` 垂直精度和 `3 m` 趋势阈值在不同设备、天气、城市峡谷和后台采样条件下表现可能不同。
- 不使用气压计或数字高程模型时，无法保证与其他运动 App 的累计爬升完全一致。
- 海拔范围可能出现小于 `3 m` 的跨度而累积升降为 `0 m`；这是因为范围描述观测极值，趋势阈值描述可累计变化，两者口径不同。

以上限制不得通过伪造数据、静默外部补算或隐藏不可用状态规避。
